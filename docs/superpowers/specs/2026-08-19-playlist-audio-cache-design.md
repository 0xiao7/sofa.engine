# 官網複習播放清單正式音檔快取設計

日期：2026-08-19
狀態：設計已由使用者核可，待書面規格審閱

## 目標

讓 `dashboard.html` 的「今日複習／播放清單」在 iPhone Safari 與一般瀏覽器中，以可重複取得、可顯示真實時長、可連續播放的正式 MP3 為主要播放來源。裝置內建朗讀只作故障備援，不再是正常路徑。

本工作只處理官網複習播放清單，不修改 Podcast、YouTube Podcast、社群排程或其他內容發布流程。

## 現況與根因

正式站 `/api/playlist` 目前可回傳播放項目，但 `audio_url` 為空，僅提供 `lazy_audio_url`。前端點擊播放後才向 `lazy-audio.mp3` 取得音訊；若請求或播放失敗，便退回 `SpeechSynthesisUtterance`。

這使使用者在音訊 metadata 尚未載入時看到 `0:00 / 0:00`，也讓首次等待、聲線與錯誤回饋依裝置狀態而變動。正式站抽驗的 lazy endpoint 可產生 MP3，但目前 API 沒有把快取狀態、音檔版本與可用時長作為穩定契約回傳。

## 採用方案

採用「首次生成、版本化持久快取、後續直接播放」：

1. 播放清單 API 仍快速回傳文字內容與播放入口。
2. 音檔端點以內容版本鍵查找正式快取。
3. 命中快取時直接串流既有 MP3。
4. 未命中時只允許單一生成者製作音檔；同一版本的並行請求共用結果，避免重複計費與競態寫入。
5. 生成成功後以原子方式寫入持久儲存與 metadata，之後所有請求直接命中。
6. 生成失敗時不寫入損壞或零長度檔案，回傳可辨識的錯誤；前端才啟用裝置朗讀備援。

不採完全即時生成，因其無法解決首次延遲與裝置差異；也不採一次生成全法規，因範圍、成本與失效重建量過大。

## 音檔版本鍵

每個快取物件必須由下列輸入的穩定雜湊決定：

- `page_id`
- 法規名稱與條號
- 實際送入 TTS 的分段文字
- `content_layer`
- 問題後停頓秒數
- provider 與 voice ID
- 語速、音高、取樣率與編碼設定
- 音檔格式版本

任何輸入改變都產生新版本，不覆寫舊版本。舊版本可延後依保留政策清理，但不得在新檔完成前破壞目前可播放版本。

## 後端契約

`GET /api/playlist` 的每個 item 應回傳：

- `audio_url`：已就緒的固定版本網址；未就緒時可為空。
- `audio_status`：`ready`、`preparing`、`fallback_only` 或 `failed`。
- `audio_version`：版本鍵或其不可逆縮寫。
- `audio_duration_seconds`：已驗證音檔的真實時長；未知時為 `null`。
- `lazy_audio_url`：未就緒時的生成／取得入口，保留向下相容。
- `audio_provider` 與 `tts_voice`：實際產製來源，不得把備援裝置朗讀標成正式音檔 provider。

音檔端點必須：

- MP3 成功時回傳 `200 audio/mpeg`、非零 `Content-Length`、版本 ETag 與合理快取標頭。
- 已有快取時不得再次呼叫 TTS。
- 生成中時採有限等待或明確 `202` 契約，不回傳假的 MP3。
- 生成錯誤時回傳結構化錯誤與可追蹤 request ID，不把錯誤 HTML 當音檔。
- 驗證輸出可被解碼、時長大於零，才將狀態切為 `ready`。

## 前端播放狀態

播放器採明確狀態機：

1. `idle`：顯示 `--:--`，不以 `0:00 / 0:00` 暗示零長度音檔。
2. `loading`：顯示「音檔準備中」，鎖定拖曳但保留停止與換題操作。
3. `ready/playing`：metadata 載入後顯示真實時長，啟用進度、上一題、下一題與連續播放。
4. `paused`：保留目前時間與字幕位置。
5. `fallback`：清楚顯示「正式音檔暫時無法載入，改用裝置朗讀」；裝置朗讀不顯示假的可拖曳音軌。
6. `error`：兩條播放路徑都失敗時，保留文字、練習與法條入口，提供一次重試。

使用者切換題目或重新整理清單時，舊請求、舊 audio element 與舊字幕計時器必須取消，不能覆寫新題狀態。

## 字幕與停頓

- 正式音檔以後端回傳的 `lyric_lines` 與真實時長同步。
- 問題、思考停頓、答案三段至少各有一個可追蹤區間。
- 停頓已包含在正式音檔時，前端不得再額外等待一次。
- 裝置朗讀備援才沿用前端 pause timer 與提示音。
- 連續播放必須等當前正式音檔 `ended` 後再進下一題。

## 快取儲存與營運安全

- 持久快取必須使用部署後仍保留的物件／檔案儲存；不得只寫 Render ephemeral filesystem 後宣稱完成。
- 快取 key 不包含使用者識別資訊，音檔也不得含會員或答題個資。
- 同一內容版本可跨使用者共用。
- 設定單檔大小、生成時間與文字長度上限，超限時 fail closed。
- 記錄 cache hit、cache miss、generation success/failure、生成耗時與播放端錯誤類型；不得記錄完整私人答題內容。
- 部署時保留現有 lazy endpoint 相容性，先讓新前端讀新欄位，再逐步預熱高頻項目。

## 測試策略

實作必須測試先行，至少涵蓋：

### 後端

- 相同版本第一次生成、第二次命中，TTS 只呼叫一次。
- 不同文字、聲線或停頓秒數產生不同版本。
- 並行相同請求不會重複生成或留下半成品。
- TTS 失敗、零長度或不可解碼輸出不會標記 `ready`。
- API 正確回傳狀態、固定 URL、時長、provider 與版本。
- 不可接受的參數、過長文字與不存在的 page ID 會 fail closed。

### 前端

- metadata 前顯示 `--:--`／準備中，metadata 後顯示實際時長。
- `audio_url` 優先於 `lazy_audio_url`。
- 正式音檔失敗才啟用裝置朗讀，並顯示備援狀態。
- 換題會取消舊請求與舊播放狀態。
- 播放、暫停、拖曳、上一題、下一題、連播與字幕同步符合狀態機。
- 裝置朗讀模式不呈現假的 duration 或可拖曳進度。

### 正式環境驗收

- 免費模式載入至少五筆播放清單。
- 每筆固定或生成入口回傳可解碼的 MP3、HTTP 200、非零大小與正時長。
- 同一音檔第二次請求可從快取取得，版本 URL／ETag 穩定。
- iPhone Safari 實機或等價 WebKit 行動驗收：首次播放、重播、背景回前景、下一題與連播。
- 使用者截圖所示商業會計法第 2 條不再停留於無說明的 `0:00 / 0:00`。
- 正式站 `dashboard.html`、API 回傳與實際音檔三層證據一致。

## 發布與回復

1. 先部署後端向下相容欄位與快取邏輯。
2. 驗證舊前端仍能使用 `lazy_audio_url`。
3. 再部署前端狀態機與新欄位讀取。
4. 預熱少量高頻播放項目並完成 iPhone Safari 驗收。
5. 若新前端異常，可回退前端而保留相容後端；若快取服務異常，API 回到 `fallback_only`，不得回傳損壞音檔。

## 完成定義

只有同時符合以下條件才能標記完成：

- 後端與前端新增回歸測試先紅後綠，完整相關測試通過。
- 正式快取可跨部署持久保存，並有一次 miss 後 hit 的證據。
- 正式站五筆抽樣音檔可解碼、可播放且真實時長可見。
- iPhone Safari 播放與失敗備援均通過。
- 沒有修改 Podcast 或其他發布流程。
- TASK_DB、CHANGELOG_DB（是否公告=false）與本機 SoFa 控制文件完成同步。
